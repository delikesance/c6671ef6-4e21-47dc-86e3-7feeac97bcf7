# Native thread migration

Official pages read before implementation on 2026-10-04: [$startThread](https://wiki.botdesignerdiscord.com/bdscript/startThread.html), [$editThread](https://wiki.botdesignerdiscord.com/bdscript/editThread.html), [$threadAddMember](https://wiki.botdesignerdiscord.com/bdscript/threadAddMember.html), [$threadRemoveMember](https://wiki.botdesignerdiscord.com/bdscript/threadRemoveMember.html), [$threadMessageCount](https://wiki.botdesignerdiscord.com/bdscript/threadMessageCount.html), [$threadUserCount](https://wiki.botdesignerdiscord.com/bdscript/threadUserCount.html). Discord constraints were checked against the [channel resource](https://docs.discord.com/developers/resources/channel) and installed nyxx 6.9.0+1 builders/models. The legacy interpreter was not used as the contract.

startThread accepts 3–5 arguments, including its required but emptiable message position. Optional archive duration defaults to 60; optional return flag defaults to no. An empty message creates a public thread explicitly, avoiding Discord's historical private-thread default; a supplied message uses the linked-message endpoint. Only text/announcement parents are supported. Announcement creation requires a source message. Forum/media creation requires initial content unavailable in this BDFD signature, so those parent types reject.

editThread accepts 1–6 arguments and maps name, archived, archive duration, locked and slowmode. Omitted fields and !unchanged stay absent from SDK update payloads, including the slowmode sentinel. Bool values use yes/no; archive durations accept 60/1440/4320/10080; slowmode accepts 0–21600 seconds. Member functions require two IDs and emit empty text. Counts accept no arguments and pass the current context channel ID, falling back to the service's current channel only when context is absent.

BotThreadService is typed and independent of script/block evaluation. DiscordBotThreadService exposes read-only prepareThreadCreation, prepareThreadModification and prepareThreadMemberChange methods, reused by its mutations and available to fixture-backed adapters. They return the validated parent GuildChannel or Thread. Entity/permission reads are fresh via DiscordBotPermissionQueryService, which computes parent overwrites and guild/member roles. Shared budget checks surround reads and each write. No retries or fictional rollback occur after a write failure.

Creation requires effective View Channel and Create Public Threads. Adding requires Send Messages in Threads; removal requires Manage Threads except for the private thread creator. Archived threads reject membership changes rather than implicitly unarchiving. Archived editing requires archived=false in the request. Unarchive-only on an unlocked thread uses Discord's documented Send Messages allowance; other edits require Manage Threads. The BDFD restriction against locking archived threads checks the resulting archived state.

## Interpretation and limits

threadMessageCount's introductory sentence says users, whereas its name/example text and illustrated result say messages. The implementation follows the example and returns message_count before the command response is sent. Discord excludes the parent source message and deleted messages; this is distinct from total_message_sent. Threads created before July 2022 can have inaccurate message counts above 50. threadUserCount uses the approximate member_count field capped at 50 rather than an intent-dependent member-list traversal. BDFD's exact behavior above that cap is unverified.

The wiki does not specify explicit empty optional fields, boolean case sensitivity or mutation return text. Explicit empty optional creation/edit values reject; omitted values and !unchanged preserve edit fields. Yes/no is case-insensitive; marker matching is exact apart from surrounding whitespace. Edit/member mutations return empty text. These are local edge decisions, not backend-confirmed BDFD behavior.

The edit wiki mentions old boost requirements for three/seven-day archives; current Discord documentation lists all four durations without that gate. The service accepts them and lets Discord enforce additional server capabilities. Invitation target access, private invitable settings, source-message existence, duplicate linked threads and capacity limits are ultimately enforced by Discord. Parent overwrites alone do not emulate private-thread membership access; a fresh successful thread fetch establishes visibility for a real Discord client, while fixture visibility remains incomplete. Explicit IDs are not restricted to the current guild because the wiki does not require that restriction. Positive decimal snowflakes are validated; values outside the SDK's signed integer representation fail with a typed argument error. No audit-reason parameter is invented.

## Validation

15 dedicated tests pass: official defaults/examples, omitted SDK fields, membership/count bindings, invalid arguments before effects, arity preflight, unknown opaque arguments, SDK payloads, archived rejection, permission failures, private creator removal, unarchive-only permission allowance, fresh metadata reads, no retry and expired budget. Targeted analysis reports no issues. Tests use mocks; no real Discord requests occur.
